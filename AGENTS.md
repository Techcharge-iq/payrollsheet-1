# Project rules

- Payroll uses the existing external database; do not apply payroll infrastructure repairs to the unused managed database because they will not affect the app.
- Salary rate selection lives in `src/lib/salary-history.ts` and ignores undated legacy records so schema repair cannot invent historical salary dates.
- New salary-history writes use `effective_from`; Workforce normalizes legacy dates through the payroll helper so saving, display, and rate selection agree.
- Timesheet attachments use a private bucket with user-prefixed paths and signed URLs, preserving document privacy without anonymous read access.
- Monthly attendance prefills new days from the date's deployment as a whole before attendance-history fallback; persisted days remain authoritative to preserve recorded allocations.
- Food generation uses food-calendar.ts to suggest calendar-day site allocation using dated deployments, then attendance fallback; legacy positive defaults enable the daily policy and explicit zero settings remain exemptions. Saves accept any non-negative entered food amount because users may deliberately deduct more. Paid history is never recalculated.
- Annexure A requires an explicitly selected site and reads canonical timesheets by project identity, with exact normalized site-name fallback for legacy records; partial names must never combine separate projects. Page timesheet and employee reads in stable ID order until exhausted, failing on any page error, so API row limits cannot silently truncate reports.
- Use `fetchAllPages` for uncached attendance, deployment, roster and salary-history lists, adding a unique ordering key to existing sort order; complete reads prevent silent row-limit losses without changing access policies or settled data.
- Payroll save errors for the legacy employee-month constraint must identify the external schema repair, never suggest overwriting prior payroll; site-lock warnings describe inclusion, not payment status.
- Multi-site payroll helpers aggregate prior-month food across site lines and reserve other batches' advance recoveries for entry/import/approval; draft allocation fallback uses batch site identity, while settled fallback remains unchanged.
- Payroll-line saves run a fresh site/month duplicate preflight before ID-based upsert; database uniqueness remains required for concurrency and the external legacy constraint must be replaced separately.
- Payroll deletion eligibility is shared by both screens and the server: unpaid Draft/Review/Approved/Legacy batches require confirmation; any payment marker, nonzero amount or Locked/Paid status protects the batch, and deletion uses an atomic database operation.
- Server payroll saves canonicalize month from the target batch and verify last-site advance recovery and remaining/net-earnings caps from fresh records; paid saves are rejected and concurrency still requires external database enforcement.
- Protect payment-bearing employee lines individually during form saves and refresh; skip them rather than rewriting them, keep batch identity/deletion protected, and allow only authorised forward status transitions with fresh payment checks (Mark paid never requires editing protected partial payments), so unpaid coworkers remain editable without altering paid history.
